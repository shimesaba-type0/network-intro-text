# ADR-001: Web/PDF公開パイプラインおよび図版制作方針

**Status:** Accepted
**Date:** 2026-08-10
**Deciders:** Takashi Kouno
**Refs:** [shimesaba-type0/network-intro-text#2](https://github.com/shimesaba-type0/network-intro-text/issues/2)

---

## Context

IT研修のテキストを制作し、Web版と印刷用PDF版の両方を提供したい。

**プロジェクトの性質:**

- Markdownファーストで、GitHub中心の制作フロー（バージョン管理・差分レビュー・issue管理）を維持したい
- takashi-works.com（名刺サイト）は既にAstro + Cloudflare Workersで構築されており、問い合わせフォーム・MCPサーバー・レート制限KV等を担う複雑な自前Workerを抱えている。テキストはこの構成に手を入れずに切り離して運用したい
- 印刷を希望するお客様を想定し、PDF出力は妥協したくない。ただし手間が大きく変わるなら見送る判断もあり得る
- フローチャート・シーケンス図・状態遷移図・ネットワーク構成図など、複数種類の図版が必要
- テキストは今後複数本（Linux入門、ネットワーク入門、…）に増える見込み

**制約:**

- 1人で執筆・運用する前提。設定はシンプルに保つ
- テキストが増えてもインフラの運用コストが線形に増えない構成にしたい

---

## Decision

**レンダラー:** Vivliostyle CLI（Single Source Multi Output）を採用。Markdown原稿1本からWebPub(HTML)とPDFを同時生成する。

**ホスティング:** GitHub Pages。1テキスト=1リポジトリとし、テキストが増えてもCloudflare Workers等のインフラを追加しない。

**図版:** 作成ツールを用途で使い分ける。

- シーケンス図・状態遷移図（例: TCP 3-way handshake）など時系列・関係性中心の図 → Mermaid
- ネットワーク構成図など配置に意味を持たせたい図 → draw.io
- いずれも最終原稿には**事前にSVGへレンダリングした画像として**埋め込み、レンダラー側にMermaid/draw.ioを直接解釈させない

**Web版の公開方法:** Vivliostyle Viewerは自己ホストせず、公式（`vivliostyle.org/viewer`）へのリンク方式で運用する。Viewer自体のメンテナンス（更新追従）が不要になる代わりに、公式サービスの可用性に依存する。

**コンテンツライセンス:** Viewerを自己ホストしないため、AGPLv3をリポジトリ全体に適用する必要はないと判断。テキスト本文は**CC BY-NC-ND 4.0**（表示 - 非営利 - 改変禁止）で運用する。

- **表示（BY）**: 著作権者（Takashi Kouno）のクレジット表示を求める
- **非営利（NC）**: 商用利用には別途許諾が必要。ただし公開ライセンスはあくまで不特定多数向けのデフォルト条件であり、著作権者自身が個別の相手（友人・後輩等）に無償・優遇条件で利用を許諾することは自由に行える（ライセンス文言側での例外規定は設けない）
- **改変禁止（ND）**: 内容の正確性への責任を著作権者に一本化するため、改変しての再配布は禁止する。改善提案はissue/PRの形で受け付け、取り込むかは著作権者が判断する

**表記の掲載方法（3階層）:**

- Web/PDF共通のフッター（全ページ）: `© Takashi Kouno · CC BY-NC-ND 4.0` の1行（年は毎年のメンテが発生するため入れない）+ legalcodeへのリンク
- Web/PDF共通の専用ページ（1箇所）: フルの説明（各条件の噛み砕いた説明）
- PDFの奥付（巻末1ページ）: フルの説明

この表示は第三者の無断利用を制限するものであり、著作権者自身の利用（販売・研修利用等）を制限するものではない。

**ブランチ運用:** 執筆用ブランチ → PR（プレビューでWeb/PDF両方を確認） → main（マージで本番デプロイ）の2段階。公開前の中間確認用ブランチは置かない。

**開発環境:** Claude Code on the web（端末非依存）。

## Options Considered

### レンダラー

#### Option A: VitePress

| 観点 | 評価 |
| --- | --- |
| Mermaid対応 | プラグインで標準的にサポートされている |
| draw.io由来のSVG埋め込み | 通常の画像参照で問題なし |
| PDF/改ページ | 標準機能なし。コミュニティ製プラグイン（vitepress-export-pdf等）はPuppeteerでのブラウザ印刷を自動化しているだけで、正式なCSS組版ではない |
| 日本語タイポグラフィ | デフォルトテーマはラテン文字前提。Noto Sans JP等のCSS当てが別途必要 |

**Pros:** Web版・PDF版を同一パイプラインで生成でき、PDFの組版品質が高い
**Cons:** Mermaidの直接埋め込みは非対応。VFM独自拡張への依存は将来の移行コストになり得る

#### Option B: Vivliostyle CLI（採用）

上記「Decision」に記載の通り。

### Viewer提供方法

#### Option A: 自己ホスト（Viewer配布パッケージをリポジトリに含めてGitHub Pagesで配信）

**Pros:** 公式サービスの可用性に依存しない
**Cons:** Viewerの更新に自分で追従する必要がある。AGPLv3のコードをリポジトリに持ち込むことになり、リポジトリ全体のライセンスとの関係を整理する手間が生じる

#### Option B: 公式Viewerへのリンク方式（採用）

**Pros:** メンテナンスフリー（公式が更新すれば自動的に反映される）。AGPLv3のコードを自リポジトリに持ち込まないため、ライセンス上の論点が発生しない
**Cons:** vivliostyle.orgの可用性に依存する

### コンテンツライセンス

#### Option A: 独自の著作権表示のみ（© + 無断転載・商用利用禁止）

**Pros:** 文言をゼロから自由に決められる
**Cons:** 「営利」の範囲や許諾の取り方が曖昧になりやすく、読み手（特に企業側）が扱いに迷う。国際的に確立された枠組みではないため、都度説明が必要になる

#### Option B: 完全に開放（CC BYやCC0など、商用利用も改変も許可）

**Pros:** QRコードのように広く流通することで認知・信用の獲得を狙える
**Cons:** テキスト自体を商品として販売する道を事実上手放すことになる。改変されての再配布も止められず、内容の正確性への責任の所在が曖昧になる

#### Option C: CC BY-NC-ND 4.0（採用）

**Pros:** LPI-Japanの「Linux標準教科書」シリーズ等、日本のLinux教育分野で既に確立された前例がある。国際的に定義されたライセンスのため説明コストが低い。改変は著作権者に一本化しつつ、非営利利用は自由に許容できる
**Cons:** 「非営利」の境界線について、LPI-Japanのような詳細な定義文言を独自に作り込むかどうかは別途検討が必要。個別相手への優遇条件は都度、口頭等での直接許諾が必要（ライセンス文言では対応しない）

### 図版の作成ツール

#### Option A: Mermaid一本化

**Pros:** テキストソースなのでdiffが読みやすい、GitHub上でコードフェンスがそのままプレビューされる
**Cons:** `graph`/`flowchart`系は内部でdagreによる自動レイアウトを使うため、ノード位置を明示的に指定できない。再描画のたびに位置がズレることがあり、ネットワーク構成図のように配置に意味を持たせたい図には向かない

#### Option B: draw.io一本化

**Pros:** 位置情報を完全に制御でき、後から調整もしやすい。表現力が高い
**Cons:** シーケンス図・状態遷移図のような時系列表現は、Mermaidに比べて記述の手間が大きい。XMLはdiffで追いづらい

#### Option C: Mermaid + draw.ioの使い分け、事前SVG化（採用）

**Pros:** 図の性質に応じて得意なツールを使え、かつ最終的にはどちらもSVG画像に変換されるため、レンダラー側（Vivliostyle）のMermaid非対応問題も同時に解消される
**Cons:** 図の作成フローが2種類になり、SVGへの変換ステップ（mermaid-cli実行、draw.ioからのExport）が運用に組み込まれる

---

## Trade-off Analysis

最大の論点は**Web版とPDF版、どちらを優先するか**だった。VitePressを選べばMermaidも含めた図版対応の幅は広がるが、PDF出力は簡易的な代替にとどまり、紙のテキストとして販売・納品できる品質にはならない。Vivliostyleを選べばPDFの組版品質は確保できるが、Mermaidの直接利用ができない。

この対立は、図版を**事前にSVGへレンダリングしてから埋め込む**という運用ルールを敷くことで解消した。Mermaid・draw.ioのどちらで作図しても、レンダラーに渡す時点では単なる画像になるため、レンダラー選定の判断軸から「Mermaid対応の有無」を切り離せる。残った判断軸は「PDFの組版品質」のみであり、印刷用途を重視する以上はVivliostyleを選ぶのが合理的と判断した。

「Web版とPDF版、手間がほとんど変わらないなら両方作っておくべき」という判断も、この解消によって成立している。図版の事前SVG化という追加の一手間はあるが、それを踏まえてもレンダラー1本でWeb/PDF同時生成できる構成の方が、VitePress + 別PDFパイプラインの二重管理より総コストが低いと見込んだ。

## Consequences

**楽になること:**

- Markdown原稿1本からWeb版・PDF版を同時に生成でき、二重管理が発生しない
- 図版の作成ツールを都度最適なものに選べる（位置制御が要る図はdraw.io、時系列表現はMermaid）
- テキストが増えてもリポジトリを追加するだけで、Cloudflare等のインフラを増やす必要がない
- PRプレビューでWeb/PDF双方を確認できるため、公開前の中間ブランチが不要になる

**難しくなること / 注意点:**

- 図版はMermaid/draw.ioで作成後、SVGへの変換ステップ（mermaid-cli実行、draw.ioからのExport）を都度挟む必要がある
- VFM独自拡張（ルビ・独自脚注・独自fenced div）は使用を避けるか、使う場合は他ツールへの移行コストとして許容する
- PRプレビューを機能させるには、GitHub PagesのデプロイソースをClassicな「Deploy from a branch」方式にする必要がある（`rossjrw/pr-preview-action`は「GitHub Actions」デプロイ方式とは非互換）
- vivliostyle.orgが停止・変更された場合、Web版の閲覧導線が影響を受ける（自己ホストしない選択のトレードオフ）

**将来見直すべきタイミング:**

- Mermaid側の対応が進み、Vivliostyle CLIが公式にMermaidをサポートするようになった場合、事前SVG化の一手間を省けないか再検討する
- モバイルでのVivliostyle Viewer閲覧性に問題が見つかった場合、Web版の提供方法を再検討する
- テキストの本数が増え、リポジトリ間でのデザイン・ナビゲーション共通化の負荷が無視できなくなった場合、共通テーマパッケージ化を検討する
